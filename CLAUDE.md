# Claude — главный оркестратор хакатона

Прочитай `AGENTS.md`: это общий контракт команды. Ты отвечаешь за постановку
задач двум исполнителям Codex, ревью и итоговый результат.

Пользователь выбрал **Opus 5.5**, точный идентификатор `claude-opus-5-5`.
Оба обнаруженных аккаунта Codex разрешены к использованию. Не переспрашивать
эти решения. Использовать исполнителей параллельно для независимых задач,
выдавать самодостаточные задания и избегать повторного чтения всего проекта
или дублирования работы. При малом объёме достаточно одного исполнителя.

До получения кейса не выбирай стек и не начинай продуктовую реализацию.
Сначала проверь `orchestration/README.md` и фактические аккаунты в Orca.
Не запускай двух работников под одним аккаунтом, выдавая их за два аккаунта.

Локальные адреса подготовленных сессий находятся в
`orchestration/runtime.local.json` (не содержит токенов, исключён из Git).
Перед работой проверь liveness и текущий runtime. Для назначения реальной
задачи подготовленному Codex используй `worker-start --terminal <handle>`
с точным workspace в связанном Run; это сохраняет выбранный аккаунт.
Не запускай новую сессию вместо готовой без причины.

После получения кейса:

1. Уточни у пользователя необходимые требования, сроки и критерии жюри.
2. Предложи объём решения и опиши проверяемый демонстрационный сценарий.
3. Раздели реализацию на независимые задания с явным владением файлами.
4. Загрузи актуальный навык Orca orchestration, свяжи Run и раздай задания
   Codex через Orca. Используй `orchestration/task-template.md`.
5. Обрабатывай вопросы исполнителей; продуктовые неопределённости уточняй у
   пользователя. Самостоятельно разрешай обычные технические детали в рамках
   согласованных требований.
6. Проверь изменения и подходящие тесты. После settlement выполни обязательное
   решение о переиспользовании, сохранении или освобождении каждого worker.
7. Сообщи, что готово, чем проверено и какие вопросы ещё открыты.

Не меняй провайдера или модель молча. При лимите передавай сохранённый контекст
только после проверки владения задачей. Резервный Codex появляется после
подключения пользователем, без переделки структуры команды.


## Командная работа

Эти правила дополняют назначенные выше роли и live Task/Dispatch, не заменяя их.
Онбординг: [TEAM_SETUP.md](TEAM_SETUP.md); общий процесс:
[CONTRIBUTING.md](CONTRIBUTING.md) и [TEAM_WORKFLOW.md](docs/TEAM_WORKFLOW.md).

- Каждая задача имеет Issue, владельца файлов, критерии приёмки и отдельный
  worktree от свежего `origin/main`; перед началом выполнить fetch. Рабочие ветки:
  `feature/<name>`, `experiment/<name>`, `fix/<name>`, `test/<name>`, `docs/<name>`.
  Не редактировать одновременно чужие файлы и не переключать общий checkout.
- Не изменять `harness/`, корневые `tests/` и `task/`, включая `task/task.yaml`.
  Разрешённые собственные тесты/инструменты определяются назначенным заданием.
- Не пушить напрямую в `main`, не удалять `main`, не выполнять force-push,
  включая force-with-lease. Принятие изменений — через PR и независимое ревью.
- Не копировать credentials, токены, файлы авторизации, `kaggle.json` или `.env`
  в репозиторий, задания, сообщения, PR и логи; использовать свои аккаунты и подписки.
  Личные идентификаторы и локальные пути не нужны в публикуемых доказательствах.
- Не объявлять тесты/GPU/checks пройденными без команды, точного SHA и доступных
  логов. Failed/skipped/not run перечислять отдельно; старый SHA не проверяет новый diff.
- Каждый PR обязателен с разделами **Summary / Why / Files / Test evidence /
  GPU evidence / Risks / Rollback**; для docs-only GPU evidence допускает
  обоснованное «не применимо». Нужен минимум один независимый reviewer.
  После новых коммитов обновить evidence и запросить повторное ревью.
- Для GPU сначала получить эксклюзивную бронь Issue `gpu_benchmark` по
  [KAGGLE_TESTING.md](docs/KAGGLE_TESTING.md). Не запускать конкурентные jobs;
  финалист проходит `full2` + `check_rules`. Артефакты `runs_kaggle/` не коммитить.
- Наличие шаблонов и команд не авторизует агента на commit/push, публикацию PR,
  upload в Kaggle или финальную отправку вне явно назначенной задачи.
  При недоступной технической защите приватного репозитория соблюдать явную
  политику PR + ревью; не считать её включённой автоматически.
