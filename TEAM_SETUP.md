# Первый рабочий день: Orca и GitHub

Терминал необязателен для знакомства. Git хранит историю, GitHub — общий удалённый
репозиторий и ревью, Orca — рабочие каталоги и агентов. **Worktree** — отдельная
копия файлов задачи с собственной веткой; **commit** — локальная запись изменений;
**push** отправляет её на GitHub; **PR** предлагает принять ветку после проверки.

## Подготовка участника

1. Создайте или используйте свой GitHub-аккаунт, включите двухфакторную защиту.
   Получите приглашение от владельца и примите его через GitHub. Проверьте, что
   репозиторий открывается под вашим аккаунтом; передавать чужие пароли не нужно.
2. Установите Orca с [официальной страницы](https://www.onorca.dev/docs/install)
   для своей ОС. При желании установите
   [GitHub Desktop](https://desktop.github.com/) для операций Git через GUI.
3. Войдите в GitHub Desktop через браузер. Выберите **File → Clone repository**,
   найдите приглашённый репозиторий и выберите свой локальный каталог. URL берите
   на странице нужного репозитория в **Code**, не из чужих конфигураций.
   Если Desktop недоступен для вашей ОС, используйте доступный Git-клиент или
   необязательный терминальный вариант ниже, затем тот же Add Repo.
4. В Orca нажмите **Add Repo**, выберите клонированный каталог. В настройках
   репозитория проверьте base ref: `origin/main`. Это основа будущих задач,
   а не разрешение редактировать `main`. См.
   [первый запуск Orca](https://www.onorca.dev/docs/first-session).
5. В GitHub Desktop нажмите **Fetch origin** перед началом задачи. Для новой
   задачи используйте свежий `origin/main`, даже если локальный `main` старее.
   Fetch получает историю и не переносит чужие изменения в ваш worktree.
6. В Orca нажмите **+** у репозитория, создайте worktree на задачу. Выберите
   **Branch from: origin/main**; имя ветки задайте в **Advanced → Branch name**,
   например `docs/onboarding-check`. Если имя занято, выберите новое согласованное
   имя. Подождите завершения создания. Проверьте выбранную ветку в Source Control.
   [Модель worktrees](https://www.onorca.dev/docs/model/worktrees).
7. Выберите собственного агента: Claude Code, Codex или другого поддерживаемого.
   Установите его CLI и авторизуйтесь самостоятельно по инструкции провайдера.
   Подписки и лимиты не передаются через репозиторий. Не делитесь файлами
   авторизации и не просите агента вывести токен. Согласуйте назначение с
   координатором; этот онбординг не меняет действующие роли команды.
8. Дайте агенту ссылку на Issue, цель, допустимые файлы, запреты и критерии проверки.
   Попросите сначала прочитать `AGENTS.md`/`CLAUDE.md`. Один worktree имеет одного
   активного владельца правок; два агента не должны одновременно редактировать его.

Новый worktree не содержит игнорируемые зависимости и данные. Восстанавливайте
их разрешёнными командами проекта, а не копированием чужих секретов или compiler
cache. Orca сам не выдаёт GPU: [Kaggle-порядок](docs/KAGGLE_TESTING.md).

## Commit, Push и PR через GUI

1. Откройте diff в Orca Source Control. Проверьте каждый файл, stage только
   согласованные изменения, напишите сообщение и нажмите **Commit**.
2. Проверьте, что это ваша `docs/...`, `fix/...` или другая рабочая ветка, затем
   **Push**. Не выбирайте Force Push и не отправляйте изменения в `main`.
3. Откройте **Create PR**, выберите base `main`, заполните шаблон, назначьте
   reviewer. Draft подходит для незавершённой проверки. До одобрения не merge.
   [Операции Orca](https://www.onorca.dev/docs/review/commit-push).

Если Orca просит подключить GitHub для PR, авторизуйтесь своим аккаунтом через
предлагаемый вход. Можно вместо этого создать PR на сайте GitHub после Push.

Альтернатива — GitHub Desktop: добавьте **File → Add local repository** именно
каталог worktree задачи, а не основной clone; проверьте **Current branch**.
Вкладка **Changes** показывает diff, далее commit, **Publish branch / Push origin**,
**Create Pull Request**. Описание и reviewers удобно редактировать на веб-странице
PR. [Ветки Desktop](https://docs.github.com/en/desktop/making-changes-in-a-branch/managing-branches-in-github-desktop).
Не переключайте ветку основного checkout, пока там работает другой агент.

Веб-путь после Push: репозиторий → **Pull requests → New pull request**. Проверьте
**base: main**, **compare: ваша ветка**, просмотрите diff, заполните
описание и создайте Draft PR. Справа выберите **Reviewers**. Если такого PR ещё
нет, создайте его; если есть — обновляйте существующий, не открывайте дубликат.

## Пробный PR без изменения вычислений

- [ ] Приглашение принято, clone и Add Repo выполнены.
- [ ] Выполнен Fetch origin; создан отдельный worktree от `origin/main`.
- [ ] Ветка называется `docs/onboarding-check` или другим свободным `docs/...`.
- [ ] Согласована одна безвредная правка формулировки в `docs/TEAM_WORKFLOW.md`.
- [ ] Проверены diff, ссылки и отсутствие секретов; Python/GPU не запускались,
      это прямо указано в Test evidence и GPU evidence.
- [ ] Commit и Push отправлены только в свою ветку.
- [ ] На GitHub виден тестовый Draft PR с base `main` и заполненным шаблоном.
- [ ] Reviewer подтвердил, что видит PR и может оставить замечание.
- [ ] По решению reviewer PR либо принят, либо закрыт без merge; только затем
      worktree можно убрать. Пробный PR сам по себе не даёт права на merge.

Для проверки прав через веб можно использовать отдельную `docs/...` ветку и
кнопку редактирования документа с созданием PR. Не редактируйте эту же ветку
одновременно в браузере и локально: сначала согласуйте, какой вариант используете.

## Приглашение и защита: действия владельца

На странице репозитория: **Settings → Collaborators → Add people**, выберите
нужный аккаунт, отправьте приглашение и дождитесь принятия. Само появление
приглашения ещё не означает, что доступ получен. Для организационного репозитория
порядок доступа согласуйте с его администратором.
[Официальная инструкция GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository).

Для `main` настройте **Settings → Branches → Branch protection rule** (или
эквивалентный ruleset): PR обязателен, минимум **1 approving reviewer**, прямой
push закрыт для участников, force-push и удаление ветки запрещены. По возможности
не разрешайте обход правил и сбрасывайте устаревшие approvals после новых коммитов.
Не отмечайте несуществующие CI jobs как обязательные проверки.

Для приватных репозиториев техническая защита может требовать платного плана
владельца/организации. Если настройки недоступны, не считайте защиту включённой:
владелец фиксирует явную политику «только PR + независимое ревью, merge ответственным,
без прямого push в main, force-push и удаления». Это договорённость, а не серверный
запрет. Статус защиты запишите в командном Issue; не меняйте приватность ради обхода.
[Доступность защиты веток](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Необязательный терминал

Команды ниже выполняет участник сам, в своём worktree. Это примеры процесса,
не просьба агенту опубликовать текущую рабочую копию.

Если clone ещё не выполнен через GUI: замените `REPOSITORY_URL` на URL из **Code**
нужного репозитория, затем выполните команды. URL не должен содержать токен.
После clone добавьте полученный каталог в Orca и создайте worktree по шагам выше.

```bash
git clone "REPOSITORY_URL" team-project
```

```bash
git fetch origin
git status
git branch --show-current
git log -1 --oneline
```

Worktree создавайте через Orca от свежего `origin/main`. После согласованной
правки пробного документа и проверки ветки:

```bash
git add docs/TEAM_WORKFLOW.md
git diff --cached
git commit -m "docs: clarify team workflow"
git push -u origin docs/onboarding-check
```

Последняя команда подходит только если фактическая ветка именно такая. Затем
откройте PR через GUI. Не копируйте команды, меняющие ветку или историю, в чужую
активную сессию. Проблему с доступом решайте с владельцем, без передачи credentials.
