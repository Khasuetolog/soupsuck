Статус: реализован opt-in `SOUP_EXP_OFFLOAD_RECOMPUTE_UP=1`, default выключен.

## Гипотеза и изменение

Профиль контроля
`runs_kaggle/20261031T053053884905Z_layerprof_80f8e2e_s043/out/layer_profile.log`:
`mlp.offload.event_wait` 19.2137 ms/step forward + 37.3286 backward;
D2H 64.9918 и H2D 66.8403 ms/step. Эти цифры относятся к исходному
инструментированному запуску, не к EXP-009.

Вместо двух fp16 тензоров `[N,I]` offload сохраняет fp16 `gate [N,I]` и
`x [N,H]`. Backward восстанавливает только значение `up_proj(x)`, затем
использует прежний SwiGLU backward и **исходные** projection GradientEdges
для dx. Gate/down не пересчитываются. При каждом retained replay требуется
ещё один forward up; оригинальный down graph продолжает использоваться.

Eligible проекции уже выполняют арифметику fp16. Для dense fp32+AMP и bnb с
fp32 input восстановленный x можно передать прямо как half: dense AMP
использует те же половинные значения, bnb возвращает half без лишнего
полноразмерного fp32 up. Dtypes dgate/dup и итогового dx остаются исходными.
Recompute выполняется с captured autocast и **включённым grad** на временном
leaf-view staging x, после чего результат сразу detach. Это существенно:
локально проверенный исходник bnb 0.50.2 `matmul_4bit` выбирает другой
inference `gemm_4bit` при выключенном grad; исходный путь вызывает
`MatMul4Bit.apply`. Временный graph не сохраняется для дальнейшего dx и
не копирует staging x. Восстановленный up освобождается сразу после SwiGLU,
до projection backward/dequantization.

Pool сохраняет те же streams, events, host leases, current/next prefetch,
record_stream, запрет eviction активного reader и retained-graph lifetime.
У второго upload/host/download буфера теперь ширина H. При изменении режима
или ширины старый pool проходит существующий retirement, пока жив его graph
или незавершённые операции; старые contexts читают собственную политику pool,
а не текущую переменную окружения. Переключение режима на живых graphs может
временно держать оба pool; production A/B запускает каждый режим отдельно.

Флаг применяется только при I>=2H, чтобы снижение staging покрывало
временный up. При меньшем расширении остаётся исходный offload. Full/partial
recompute, explicit store и EXP-007 tail имеют прежний приоритет. При unset
или 0 сохраняются исходные gate/up tensors и количество staging slots.

### Совместимость с precompile

Двухаргументный `_HostSlot(capacity,width)` сохранён для существующего
`PreparedHostSlot`. Узкие slots создаёт отдельный `_InputHostSlot`, наследующий
исходный allocator, поэтому opt-in не потребляет полноразмерные заранее
подготовленные host pairs и не удерживает их storage через узкие views.
Precompile может всё равно зарезервировать 1960 MiB полноразмерных **CPU**
pinned pairs плюс узкие host slots: это дополнительная host RAM, не GPU peak.
`solution/precompile.py` вне владения и не менялся; при необходимости отдельный
эксперимент может готовить узкие pairs. Default process preparation остаётся
включённым для честного A/B.

## Ожидаемые bytes/memory deltas, не результаты измерений

Для одного слоя в каждом направлении:

- Контроль: `4*N*I` bytes; кандидат: `2*N*(I+H)` bytes.
- Delta: `-2*N*(I-H)` bytes, при H1536/I8960 **-41.43%**.
- При стандартных двух download pairs вместе с upload pool содержит три
  пары. CUDA staging delta: `-6*C*(I-H)` bytes, C — capacity pool.
- Временный восстановленный up: не более `2*N*I` bytes; staging savings
  превышают его при I>=2H и C>=N. Это оценка этих allocations, не гарантия
  фактического peak всего training/harness.
- Дополнительная работа: один fp16 frozen up forward на слой/обратный проход,
  без дополнительного up backward. По профилю контроля все up forwards
  занимают около 22.7 ms/step inclusive; overlap и wall effect неизвестны.

| H1536/I8960, 28 offloaded layers | N2048/C2048 | N800/C1024 |
| --- | ---: | ---: |
| D2H, control → candidate | 1960 → 1148 MiB/step | 765.625 → 448.4375 MiB/step |
| H2D delta | -812 MiB/step | -317.1875 MiB/step |
| Total PCIe delta | -1624 MiB/step | -634.375 MiB/step |
| Persistent CUDA staging | 210 → 123 MiB | 105 → 61.5 MiB |
| Transient up, максимум | +35 MiB | +13.671875 MiB |
| Staging + transient up delta | -52 MiB | -29.828125 MiB |

Другие allocations, allocator reservation и dequantization определяют
фактический peak. Скорость нельзя вывести из суммы inclusive transfer times.
