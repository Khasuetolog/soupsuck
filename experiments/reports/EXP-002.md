# EXP-002 — tile-local NF4 decode + Triton GEMM

Status: **NO-GO for every measured shape/direction**. T4 correctness PASS;
performance fails. Training dispatch remains empty and defaults are unchanged.
Measured implementation snapshot submitted to coordinator: `73a1372`.
No GPU job or commit was made by this worker; coordinator owns T4 execution.

## Hypothesis and implementation

Replace nested NF4 decode-to-dense plus fp16 cuBLAS with a tile-local decoder
feeding fp16 tensor-core multiplication, for supported frozen projections.
Shapes W[N,K]: (1536,1536), (256,1536), (8960,1536), (1536,8960).
Initial rows M=800 and 2048; no inference about other row counts.

`solution/kernels/nf4_gemm.py:nf4_tile_matmul_kernel` is our `@triton.jit`.
It computes X[M,K]@W[N,K].T (forward) or dY[M,N]@W[N,K] (dX).
Each packed high/low nibble is looked up in the same NF4 format table;
its block-64 scale is reconstructed using block-256 nested statistics.
Scale multiply and offset add stay separate (`enable_fp_fusion=False`).
The decoded product rounds to fp16 **before** `tl.dot` with a fp32 accumulator.
No dense W is allocated/stored by the candidate; only result Y and tile
register/shared intermediates exist. Bias, when present, is added to the fp32
accumulator before the fp16 result store. Tails are masked in M/N/K.
Four fixed launch candidates test BM=16/32, BN=32/64, BK=32/64, four warps,
two stages. No training autotuner or timing-based policy is introduced.

[Official tl.dot interface](https://triton-lang.org/main/python-api/generated/triton.language.dot.html)
accepts fp16 blocks and a fp32 accumulator. Its TF32 policy concerns fp32
operands; this experiment supplies fp16 operands and does not change global
PyTorch reduction/TF32 flags.

`solution/nf4_patch.py` registers the optional bnb matmul wrapper only when
`SOUP_EXP_NF4_GEMM=1`. With that variable unset the previous registration and
training route are preserved. Supported execution additionally requires bnb
0.50.2, sm75, contiguous fp16 CUDA X, validated nested NF4, frozen weight/bias,
canonical weight orientation, no `out=` and an explicitly approved exact shape.
Unsupported calls use original bnb; CUDA/compiler errors are not swallowed.

`APPROVED_SHAPES` starts empty. Its key is (M,original N,original K,transpose).
The flag alone does not route training work to unmeasured shapes. Forward and
dX can qualify independently. The custom first-order autograd saves packed W
and state, not X or dense W; nonapproved direction uses its previous operation.
The original bnb module remains responsible for input/output dtype conversion.

## Important baseline distinction

bnb 0.50.2 `backends/cuda/ops.py:922-985` routes M>1536 to dequant+linear.
For smaller M, `_gemm_4bit_use_custom_cuda:584+` may already select bnb's own
fused MMA according to dtype/shape/SM. Thus a candidate beating only
**decode+cuBLAS** is not automatically a win over the actual forward path.
The benchmark records both decode+cuBLAS and native bnb forward timings.
No ready-made kernel library is imported beyond the already allowed bnb;
the experimental implementation is original Triton code.

## Correctness gate, fixed before the first T4 result

The existing decoder and native bnb dequant output are compared byte-for-byte
on genuinely quantized nested weights. GEMM reductions can differ between
cuBLAS and tiled fp32 accumulation, so their output is not promised bitwise.
All candidates use the same preregistered gate:

- `torch.testing.assert_close(actual,expected,rtol=0.002,atol=0.002)`;
- finite outputs and relative L2 error <=0.001;
- report max absolute error, relative L2 and exact equality separately;
- test unbiased/biased forward and dX for all four forms and both M values;
- force benchmark-only approved configurations to check actual bnb/autograd
  integration in forward-only, dX-only and both-directions modes, using
  `[1,M,K]` inputs and identical upstream gradients against dense fp16 linear.

The elementwise gate allows a few half precision roundoff units at ordinary
magnitudes and a small absolute cancellation floor; the global 0.1% L2 gate
prevents that floor from masking a widespread inaccurate result. These are
fp16 GEMM approximation gates, not altered task/trainer/check tolerances.
Passing this microbench cannot establish training quality; a finalist still
needs the unchanged unit suites and paired full comparison. Failed candidates
are recorded, never granted larger tolerances to become eligible.

**24 cases × 4 configs = 96/96 correctness PASS**, no compile/CUDA errors;
none of the 96 GEMM outputs was bitwise-equal to cuBLAS. Maximum observed
absolute error was **0.000732421875**, relative L2 **0.00037139421328902245**,
below the preregistered 0.001 bound. The native-versus-own decoded NF4 weights
passed bytewise equality. All **24 autograd bridge scenarios** (8 forms/row
pairs × forward-only/dX-only/both) passed: worst output/dX absolute error
**0.0009765625**, relative L2 **0.00037155774771235883**. Bias paths passed too.
These are measured errors for synthetic quantized inputs, not full-model loss.

All 24 `recommend` fields are false. Even the **best configuration per case**
is **4.1219–66.0133× slower** than decode+cuBLAS; fused forward is
**3.3590–30.7693× slower** than native bnb. The most common best launch is
BM=32, BN=64, BK=32, warps=4, stages=2; M=800,N=256 forward prefers BN=32.
No direction or bias variant warrants a training experiment with this engine.
No production allowlist entry is added, and no full-run speedup is claimed.

Interpretation: eliminating a dense-weight store alone did not overcome
per-output-tile NF4 lookup/scale work and the resulting GEMM layout costs.
That is an engineering inference from this implementation's structure and
measured slowdown, **not** a measured register-spill/occupancy attribution:
no Nsight counter profile was collected. This rejects this engine/config grid,
not every possible future fused-NF4 GEMM design. Further tuning is outside
this completed initial experiment and would need a separate opt-in evaluation.

Per-case preliminary GO requires correctness and best candidate p90 below
baseline p10 in the same T4 session; forward must also beat native bnb p10.
A forward allowlist entry must use one configuration validated/winning for
both bias and no-bias cases, since bias is not part of its key. dX has no bias.
No interpolation to unmeasured M, no approval from compilation success alone.
Only after autograd and paired training checks may a measured shape be routed
in an opt-in experiment; default best-known-good remains unchanged.

GPU work, clock changes or allocator changes. Results, rejection reasons and
errors persist incrementally in `out/bench_kernels.json`; check the exit code.
