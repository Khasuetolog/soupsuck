## Изменение и основание

Обычный process precompile уже перекрывает сборку device binaries с model
setup. Однако Triton `warmup`/`compile` оставляют native launcher construction
ленивым: CPU C glue строится при первом реальном вызове. Это конкретная
ещё не перекрытая first-step работа в пределах назначенного владения;
её точная доля в 6.68 s старым логом не измерена.

`_offline_compile(prepare_launchers=True)` дополнительно вызывает исходный
`CudaLauncher(compiled.src, compiled.metadata)` для каждого descriptor.
Native constructor строит/импортирует CPU shared object в cache текущего
измеряемого запуска. Используются исходные signature, constants и metadata;
нет ручного изменения cache keys или compiler options. Одинаковые launcher
sources естественно переиспользуют native cache. Счётчик показывает число
подготовленных descriptors, **не число уникальных C compilations**.

Флаг обрабатывается только существующим `_process_compile`. Нет нового
процесса, parent preparation thread, parent JIT cache mutations, CUDA buffers,
kernel launch, cubin load, warmup или RNG. Проверки
`cuda_initialized=False` и `driver_touched=False` в child сохранены.
Обычный parent first launch сам загружает GPU binary и CPU launcher через
штатный cache. GPU tensor/code memory delta ожидается **0 bytes**;
host CPU memory/I/O могут вырасти, их время входит в wall.

Subprocess остаётся non-daemon, exit join и bounded failure packet сохранены.
`TRITON_CACHE_DIR` берётся только из текущего harness run и проверяется в
child; никакого переноса cache между запусками. При unset/0/other выполняется
прежний `_offline_compile()` без CPU launcher preparation. При explicit
`SOUP_EXP_PRECOMPILE=0` apply остаётся cold; thread mode не меняется.

Опциональные `binary_prepare_s`, `launcher_prepare_s`, `launchers_prepared`
передаются в обычный status и одной строкой печатаются в child stderr.
Это измерения данной preparation, не весь model setup и не wall gain.

Проверены первичные исходники Triton 3.6.0:
[CudaLauncher](https://github.com/triton-lang/triton/blob/v3.6.0/third_party/nvidia/backend/driver.py),
[native build/cache](https://github.com/triton-lang/triton/blob/v3.6.0/python/triton/runtime/build.py),
[CompiledKernel lazy handles](https://github.com/triton-lang/triton/blob/v3.6.0/python/triton/compiler/compiler.py).
Constructor CPU glue отделён от `CompiledKernel.run/_init_handles`, где
происходит GPU binary load; эта последняя часть не вызывается экспериментом.

CPU launcher preparation может конкурировать с загрузкой модели за CPU/I/O
или задержать ещё не готовые device variants, поэтому ускорение не заявлено.
Сколько first-step времени исчезнет из wall, а сколько переместится в startup,
покажет paired A/B. Полного разбиения ~23.42 s остатка по старым логам нет.
