## Training path and isolation

The notebook verifies the source archive, prepares the official data, then starts
`layer_profile.py`. The driver imports the unchanged official
`harness/run_task.py` helpers:

1. `load_task()` and `make_config()` produce the normal config, same training data,
   seed and settings; only the normal generated output directory differs.
2. `warm_up()` performs the same untimed package/model download warmup.
3. `common.run_logged()` starts a separate worker with the official `OFFLINE_ENV`,
   GPU 0 and allocator settings, dedicated Soup database, and fresh temporary
   Triton/Inductor caches. The whole worker has a configurable process timeout.
4. That worker sets the same `soup train --config ... --yes` training arguments (plus global `--verbose` for diagnostics), blocks optional
   unsloth imports as `_train.py` does, initializes CUDA, calls `solution.apply()`,
   installs its instrumentation, and calls the ordinary `soup_cli.cli.run()`.

`harness/_train.py`, `run_task.py`, task files, tests, and `solution/` are not edited
or monkeypatched on disk. The standalone worker implements the same Soup entry
sequence because the official jury entrypoint must remain untouched. It is a
**probe**, not `run_task --only solution` evidence or a jury score.

Training runs to its normal completion; no steps, rows, backward work, or optimizer
steps are skipped. CUDA events and native backward hooks are active only on
**1-based steps 8 through 24 inclusive**. This yields 17 measured steps when the
normal task completes. The callback synchronizes before/after each step as the
official timing callback does; individual regions never call synchronize.
Reports include the observed Trainer arguments, optimizer class, module names,
input shapes/dtypes, environment switches, source SHA and step window. Existing
gradient checkpointing/recompute settings are recorded, not modified.

Only the standalone worker installs wrappers, and restores them on exit. No
module forward/pre/backward hooks are installed: those would trigger solution
eligibility guards and profile a different path. Wrappers are placed on class
methods/functions with `functools.wraps`, preserving solution marker attributes.
Native LoRA/SDPA backward uses autograd **Node** pre/post hooks bounded by the exact
input GradientEdges. These hooks return None and do not modify gradients.
Custom autograd contexts receive string/dict attribution only, without tensors.
The recorder retains events and numeric/string metadata, not model activations.
Event handles/native node hooks are released at each measured step end.

## What is measured

Every row is tagged by phase, projection and decoder layer index. The JSON has both
`per_layer` and aggregated `by_projection` tables. Actual module paths and input
shape counts make mapping/coverage inspectable.

| Requested component | Instrumentation / categories |
|---|---|
| bnb Linear4bit forward q/k/v/o/gate/up/down | Class forward context records full module total; `MatMul4Bit.forward` retains that module's tag on its context |
| Forward dequant vs GEMM | Functional/backend dequant wrappers (including nested scale dequant); fallback `F.linear` region is `bnb.gemm` |
| Fused native bnb kernel | `_gemm_4bit_kernel_impl` is `bnb.fused_dequant_gemm`; a single fused kernel cannot be split into dequant/GEMM with events |
| MatMul4Bit backward by projection | Class backward context restores the forward tag; functional dequant is `bnb.dequant`, its `torch.matmul` is `bnb.dx_gemm`, parent is `bnb.matmul.backward` |
| LoRA A/B fwd | Exact existing `nn.Linear.forward` call, classified from actual `lora_A`/`lora_B` module path; no replacement math |
| LoRA A/B bwd | Native backward subgraph bounded by activation/weight input edges; includes native dX/dW GEMMs/casts, not another LoRA module's graph |
| Attention fwd/bwd | Native `F.scaled_dot_product_attention` core and its bounded native backward graph; q/k/v/o projections are their own rows |
| SwiGLU / MLP | `_FrozenMLP` totals, `swiglu_fused_forward` and `swiglu_fused_backward` separately |
| Offload | Pool store/prefetch/tensor regions; actual stream `wait_event` timed on the waiting stream; actual cross-device `Tensor.copy_` split into H2D/D2H on their current streams |
| Fused CE | `_FrozenLinearCrossEntropy.forward/backward` totals including head GEMMs, stats/compaction and CE kernels |
| Norms | `_RMSNorm` and `_AddRMSNorm` forward/backward; fused add+norm stays one region |
| RoPE | Additional `_RoPE` forward/backward rows, separate from the SDPA core |
| Optimizer | Step pre/post hooks on the underlying actual optimizer (unwrapped from Accelerate), without changing its args |

The backward LoRA and attention graph boundaries include native bookkeeping
nodes/casts; their call counts are **node invocations**, not the number of modules
or individual GEMMs. Whole-module LoRA fwd counts are module invocations. SDPA is
the attention core; native KV repeat/layout and residual bookkeeping outside that
core are not falsely labeled as SDPA kernel time. Large `bnb` totals minus its
specific children can contain scale addition, allocation/casting, bias and CPU
launch gaps, not a hidden extra GEMM.

## Timing arithmetic: avoid double counting

A CUDA-event region is elapsed stream time, including queue stalls and CPU launch
gaps between its events. It is not a hardware SM-active measurement. Events are
resolved only after the ordinary step-end device synchronization.

Each report row contains:

- `calls`, `inclusive_ms` / `inclusive_ms_per_step`: whole timed regions, nested
  totals included. **Do not sum inclusive rows.**
- `exclusive_stream_ms`, `ms_per_step`, `percent_step_wall`: intervals partitioned
  per stream, preferring a specific operation to its aggregate parent, then the
  deepest active child. This avoids subtracting nested dequant/GEMM twice.
- Projection totals are across all layers. Per-layer tables remain available in JSON.

Offload side streams can overlap the compute stream. Consequently summed
`exclusive_stream_ms` and row percentages can exceed step wall / 100%; that is not
an arithmetic error. The JSON exposes both quantities the task asks to inspect:

- `raw_wall_minus_stream_sum_ms`: literal wall minus the sum of disjoint times on
  individual streams; can be negative from overlap.
- `union_event_span_ms`: cross-stream union of recorded intervals.
- `unattributed_or_idle_ms = max(0, wall_ms - union_event_span_ms)`: the remaining
  observed wall time, without nested/parallel double counting.
- `gpu_idle_exact_ms = null`: exact physical GPU idle cannot be established from
  these Python-region events. The residual includes uninstrumented work, CPU work,
  launch gaps and potential idle; even covered regions can contain CPU-launch idle.

This distinction is required for an honest result; the script does not fabricate
an exact GPU-idle figure or treat inclusive sums as additive hardware utilization.
Per-step values and means are retained, not only one averaged table. Percentages
use the instrumented measured step wall as their denominator, not an old 0.50 s
baseline or a different machine's timing. Instrumentation adds overhead and may
perturb overlap; confirm any proposed optimization with the paired runner/full2.

## S-043 — first-step recursion regression and diagnostics

The first T4 probe (`3b7734e`) failed before completing step 1, not in CUDA-event
collection: `runs_kaggle/20261031T051841192582Z_layerprof_3b7734e_s042/out/layerprof_run/train.log`
shows `0/64`, a Soup crash bundle, and a friendly `RecursionError` without its
traceback. There are no valid timing measurements from that attempt.

The solution's `_patch_lazy_mlp` in `solution/patch.py` checks
`cls.forward is forward` before replacing its lazy trampoline, then dispatches
through `cls.forward(self, x)`. Wrapping that trampoline first breaks the identity
check: `probe.forward -> lazy.forward -> cls.forward(probe.forward) -> ...`.
The CPU regression reproduces this exact cycle using the actual function bodies
extracted from the repository source, then passes after the fix. This establishes
a concrete source-level cause consistent with the recorded T4 failure; the new
GPU run remains pending.

Fixes, confined to the standalone probe:

- Before adding the Qwen2MLP wrapper, recognize the actual lazy **code object**
  (`co_filename`/`co_qualname`, because `functools.wraps` masks module/qualname),
  restore its saved original, and invoke the solution's normal concrete fused-MLP
  installer. There is no dummy forward, CUDA warmup, or new tensor operation.
- An owner marker and completed-install guard make installation on the same
  recorder idempotent. A different active recorder is rejected rather than stacked.
  Original descriptors, including inheritance/static methods and the original lazy
  trampoline, are saved before mutation and restored in reverse order; double
  cleanup and reinstall are supported. Concrete solution markers are not unwrapped.
- Soup argv now uses its global verbosity flag in the correct position:
  `soup --verbose train --config ... --yes`. On failure, the driver echoes the
  **complete** worker `train.log` into `layer_profile.log`, not a tail.
