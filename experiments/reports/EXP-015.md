# EXP-015 — priority scheduling for existing offload streams

Implemented opt-in `SOUP_EXP_OFFLOAD_STREAMS=1` on HEAD `1c7126bb49d7b915795b9240442ccf9ec4737a9c`.
The two existing D2H/H2D streams use `torch.cuda.Stream.priority_range()[1]`,
the highest priority supported by the active CUDA device. Unset/0 keeps the
existing stream creation and default priority. Stream count, staging tensor
count/size, copies, events and `record_stream` calls are unchanged.

I did not split the upload into multiple D2H events. The single reusable upload
pair is overwritten only after `upload_free`, recorded after both gate and up
copies have been enqueued on D2H. Releasing it between the two transfers would
need another lifetime dependency and careful ordering for the paired source
buffers. That extra change is unnecessary to test the scheduling option and
could corrupt a later upload.

## Validation

It checks default versus highest stream priority, exact output and input
gradient equality, equal `torch.cuda.max_memory_allocated`, unchanged number of
host/device staging buffers, and equal aggregate staging elements. The test is
skipped by the existing module-level CUDA marker on CPU-only hosts.
