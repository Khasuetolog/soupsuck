# EXP-005 — spawn compiler в cache текущего запуска

Статус: opt-in реализация готова; **компиляция Triton, disk-hit/bitwise на
T4 и ускорение UNVERIFIED**. Коммит и Kaggle-запуск исполнитель не делал.

Флаг: `SOUP_EXP_PRECOMPILE=process`. Прежнее `=1` сохраняет потоковый
режим EXP-001; отсутствие флага и прочие значения оставляют обычный cold path.

## Причина и изменение

По данным координатора в `tasks/SPEED_LAB_RESULTS.md`, wave1 B снял около
5.6 s с loop, но wall изменился только на −0.46 s с CI, включающим ноль.
Гипотеза EXP-005 — вынести Python/compiler GIL в отдельный процесс. Конкуренция
за физические CPU и дисковый I/O остаётся, поэтому выигрыш не утверждается.

В process-режиме `precompile.start()`:

1. Требует явно унаследованный `TRITON_CACHE_DIR`; при его отсутствии
   выдаёт preparation error и не выбирает домашний/default cache.
2. Через `multiprocessing.get_context('spawn')` запускает один non-daemon
   compiler child. Fork и наследование родительского CUDA context не используются.
3. Child использует те же 62 descriptors EXP-001b для всех 15 production JIT.
   Native `create_function_from_signature` и `kernel._pack_args` формируют
   те же signature/constants/attrs/options. Никакие `D`/`==1` specialization
   tags вручную не создаются. `debug` и instrumentation добавляются как в
   JITFunction.run, compiler keyword presence/order берётся из launch sites.
4. Вместо `warmup()` child вызывает `triton.compile(ASTSource(...),
   target=GPUTarget('cuda',75,32), options=...)`. CUDA tensor allocations,
   CUDA runtime/streams, GPU launches, pinned allocation и device caches
   в child не нужны. Возвращённые CompiledKernel не запускаются.
5. Parent не получает и не подменяет JIT entries: на первом настоящем вызове
   обычный JIT читает бинарь из дискового cache этого запуска. Launcher/module
   initialization в parent всё ещё может потребоваться.
6. Parent сохраняет прежнюю фоновую pinned preparation EXP-001. В child
   она не запускается. Политики/размеры MLP pool и алгоритмы кернелов не менялись.

В конце offline compilation проверяются `torch.cuda.is_initialized()==False`
и отсутствие active/default Triton driver. Эти проверки состояния сами не
инициализируют runtime. CPU-only путь **выведен из API-исходников**, а не
заявлен как подтверждённый запуском Triton на локальном macOS без torch.

Один результат передаётся через Pipe: число подготовленных описаний, ошибки,
CUDA/driver state. Пакет ограничен <4096 bytes, чтобы без polling в training
дочерний процесс не завис при send и последующем parent-exit join; полные
ошибки печатаются в унаследованный stderr/train.log. `status()` получает
результат неблокирующим polling, показывает pid/exitcode/alive; `wait()` —
только для тестов/ручной диагностики, training его не вызывает.

Non-daemon multiprocessing children присоединяются при нормальном завершении
родителя, поэтому незаконченная compilation входит в wall time. Если child
не успел до реального launch, foreground может скомпилировать вариант обычным
способом; никакая работа модели не пропускается. Child failure не меняет
production kernels, но означает провал preparation и должен учитываться
при разборе результата эксперимента.

## Cache и измеряемый запуск

Просмотрены неизменённые `harness/run_task.py:98-111` и
`harness/common.py:103-118`:

- Каждый `train()` удаляет старый run_dir, создаёт новый и задаёт
  `TRITON_CACHE_DIR=str(run_dir/'triton_cache')`.
- `run_logged()` передаёт env непосредственно training subprocess через
  `Popen(...,env=env)`. Spawn child наследует именно это окружение.
- EXP-005 не создаёт собственный альтернативный каталог, не копирует cache
  и не использует файлы другого запуска. Child дополнительно проверяет
  совпадение унаследованной строки TRITON_CACHE_DIR с переданной parent.
- Training subprocess работает в отдельной process group; child остаётся
  в ней. Timeout/cleanup harness вызывает kill_group. Сам эксперимент не
  запускает сторонних фоновых сервисов и не меняет harness.

В unit-тесте создаётся новый пустой cache root внутри tmp_path текущего теста,
чтобы предыдущие unit cases не могли подменить доказательство disk hit.
Это не путь, используемый в paired training: там берётся только harness env.

## Основания в Triton 3.6

Использованы первичные исходники tag v3.6.0:

- [runtime/jit.py](https://github.com/triton-lang/triton/blob/v3.6.0/python/triton/runtime/jit.py):
  `create_binder()` запрашивает active target, поэтому offline child его
  обходит; native binder и `_pack_args()` вызываются с explicit backend.
- [compiler/compiler.py](https://github.com/triton-lang/triton/blob/v3.6.0/python/triton/compiler/compiler.py):
  explicit target устраняет запрос driver target; CompiledKernel handles
  инициализируются лениво. `compilation.listener` получает `cache_hit=True`
  при metadata cache hit, `False` после реальной compiler pipeline.
- [NVIDIA backend](https://github.com/triton-lang/triton/blob/v3.6.0/third_party/nvidia/backend/compiler.py):
  CUDABackend использует explicit target arch; версия ptxas получается
  CPU subprocess, runtime device query для этого пути не требуется.
- [runtime/driver.py](https://github.com/triton-lang/triton/blob/v3.6.0/python/triton/runtime/driver.py):
  DriverConfig хранит lazy `_active`/`_default`, проверяемые после compilation.

У JIT cache hook другая семантика: он вызывается и перед загрузкой compiler
disk-cache, поэтому его invocation count не равен числу реальных компиляций.
Для EXP-005 тест считает именно listener events с `cache_hit=False`.

## Тесты

`solution/tests/test_precompile.py` расширен:

- CPU: process-mode требует run cache; выбирает именно spawn; target получает
  унаследованный путь; Process non-daemon; повторный start не создаёт child.
- CPU: child отклоняет несовпадающий cache до compilation; failure packet
  ограничен <4096 bytes, полный diagnostic остаётся в stderr.
- Реальный spawn smoke локально: child запустился, унаследовал cache env,
  сообщил `ModuleNotFoundError: No module named 'torch'`, parent его join-нул
  и получил exitcode=1. Это PASS **failure/lifecycle path**, не compilation.
- CUDA suite теперь параметризован thread/process. Process-case начинается
  с пустых parent in-process entries и нового пустого test-run disk cache,
  ждёт child и требует exitcode=0, все 62 warmups, отсутствие ошибок,
  CUDA initialization=False и driver_touched=False.
- Затем реальные production wrappers вызывают все 15 JIT на N/T800/801/2048,
  H1536/I8960/V151936 с tail384, обеими norm outputs и gamma gradients,
  первым frozen residual, всеми LoRA/SwiGLU dtype cases, RoPE B1/B4,
  всеми четырьмя NF4 shapes nested/flat.
- Listener требует **ноль реальных compiler misses** и disk-hit хотя бы
  один раз для каждого из 15 имён. In-process entries до этого очищены,
  поэтому ранее скомпилированная parent binary не может дать ложный PASS.
  Outputs и gradients сравниваются побитово с обычным production call.
  Существующий thread cache-key тест и pinned ownership/bitwise тест сохранены.

Локально:

```sh

/private/tmp/s037-audit-env/bin/python -m pytest solution/tests/test_precompile.py solution/tests/test_integration.py -q -rs
git diff --check
```

Результат: **23 passed, 14 skipped**, py_compile/diff check PASS. Skips —
отсутствие torch/CUDA. GPU compiler/disk-hit/bitwise пока UNVERIFIED.
