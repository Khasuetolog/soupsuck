## Изменение

После EXP-010 child уже строит binary и CPU launcher, но parent при первом
вызове всё ещё лениво инициализирует Triton driver/binder, читает native
disk cache и создаёт `CompiledKernel`/JIT entries. Это оставшаяся работа
первого шага, которую можно перекрыть без изменения арифметики и без
предварительной загрузки GPU modules. Её доля в 2.42 s excess неизвестна;
эксперимент не обещает устранить весь excess или все 26.2 s outside.

`SOUP_EXP_PARENT_CACHE=1` в process mode добавляет non-daemon parent thread:

1. Дожидается успешного compiler child и проверяет неизменность текущего
   `TRITON_CACHE_DIR`. Другие каталоги/cache runs не используются.
2. Наследует выбранный CUDA device, уже инициализированный harness до apply.
   Если контекста ещё нет, операция пропускается с причиной в status.
3. Вызывает существующий `warmup_plan` с `MockTensor` и теми же native
   signatures/options. Native Triton JIT сам создаёт обычные device-cache
   entries; ручных cache keys, compiler options и подмены kernel нет.
4. Печатает prepared/skipped/elapsed, сохраняет wait/prepare timings в status.
   Время потоков, в том числе join при exit, остаётся внутри measured wall.

Временный per-JIT gate устанавливается до старта child. Warmup и первый
production `.run()` одного JIT защищены одним RLock. Если production уже
использовал этот JIT, оставшиеся его планы пропускаются: нельзя перепубликовать
cache entry и загрузить второй GPU module для ранее использованного варианта.
Gate снимается в finally, в том числе при ошибках; внешнюю позднюю
instrumentation wrapper не перезаписывает. Gate может кратко задержать первый
вызов, если parent warmup ещё выполняется; paired wall решает, полезен ли overlap.
Ошибки попадают в существующий preparation status, production path остаётся
обычным. Unset/0/other и thread mode не включают этот эксперимент.

Triton 3.6.0 `runtime/jit.py:695–745` при `warmup=True` пропускает launch;
`compiler/compiler.py:CompiledKernel` оставляет module/function равными None
до первого `run`/`launch_metadata`. Проверены локальные снимки исходников.
Эксперимент не обращается к этим lazy handles, не создаёт CUDA tensors,
streams/events, не делает DMA, не вызывает model forward и не расходует RNG.
Ожидаемый delta GPU tensor/workspace/code bytes: **0**; transferred bytes: **0**.
CPU metadata/IR/cache entries могут занимать больше host RSS раньше запуска;
системный RSS не объявляется неизменным. Реальный NVML GPU peak ещё не измерен.

Намеренный предел: GPU cubin warmup всех 62 descriptors мог бы загрузить
неиспользуемые variants и увеличить peak. Здесь подготавливаются только CPU
objects; GPU module load остаётся на реальном первом использовании.
Save/finite checks и k-bit casts не менялись: старые логи не обосновывают
безопасное устранение этой работы. Для точного дальнейшего разбиения нужны
timers на import/model/prepare/train/save/exit boundaries в новом профиле.
