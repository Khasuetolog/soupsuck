## Candidate and defaults

Only literal **`SOUP_EXP_NF4_FAST=1`** selects the candidate. Unset, `0`, or other
values retain `nf4_decode_kernel`, its 2048-output/four-warp launch, and existing
output/view behavior. With the opt-in set, a packed pointer aligned to four bytes
uses `nf4_decode_fast_kernel` with **4096 outputs / eight warps**. A contiguous but
unaligned storage-offset view uses the existing byte decoder. Pointer alignment
queries read host metadata, not GPU data or measurement state.

Both public nested decode and the backend's already-reconstructed flat-scale
entry select the same plan. Separate literal launch sites expose each JIT's
actual block size and compiler options to the existing precompiler. There is no new runtime tuning, caching of decoded
weights/scales, stream, warmup, test detection, or measurement-dependent behavior.

The new kernel:

1. Loads aligned uint32 words, one per eight output values. A word contains four
   consecutive packed bytes; CUDA's little-endian byte order and NF4's high-nibble
   first order give shifts `[4, 0, 12, 8, 20, 16, 28, 24]`.
2. Uses a `[64 blocks, 8 words, 8 values]` logical tile. Nested absmax/code are
   loaded once per block64 and broadcast across its 64 outputs. Flat absmax is
   likewise loaded once per block. This reduces redundant *source-level* loads;
   actual baseline load coalescing/code generation still needs GPU inspection.
3. Loads a single state2 scale for each tile. Sixty-four NF4 blocks fit within
   one block256 group, and tile starts are multiples of 64, so the tile never
   crosses a state2 group. A static assertion fixes the tile size for this proof.
4. Reconstructs scales and decodes with the same ordered fp32 operations, with
   `enable_fp_fusion=False`: `decoded = code2 * scale2; scale = decoded + offset;
   value = NF4_table[nibble] * scale; store fp16`. No summation/reassociation or
   extra rounding is introduced. The existing exact 16-value format table is used.
5. Flattens values in logical output order for contiguous fp16 stores. Vector
   store width is selected by Triton from pointer alignment/layout; vectorized
   PTX/SASS has **not** been inspected locally. Unaligned destination views remain
   supported without unsafe alignment hints.

For a partial last uint32 word, masked byte loads assemble the remaining one,
two or three bytes; no load crosses the logical `ceil(N/2)` storage. A full word
is loaded only when all four bytes exist. Odd final nibbles and incomplete NF4
blocks/output tiles are masked. Offset arithmetic and `N + 1` are promoted to
int64 before multiplication/addition to avoid int32 address overflow.

The canonical `quant_state.shape`, packed transpose shim, `out=` alias, fp16 dtype
and signed-zero semantics are unchanged. Unsupported formats/non-nested routing
remain controlled by the existing patch, not by a broader fast-path allowance.

## Memory and correctness gates

The candidate writes directly to the same destination as the current decoder.
No tensor-sized packed copy, reconstructed-scale array, decoded-weight temporary,
new GPU table or persistent workspace is allocated. Reinterpretation is a Triton
pointer cast, not a PyTorch view/copy allocation. Tile temporaries are registers;
possible compiler spills/register pressure have not been inspected without CUDA.

The test suite adds strict int16-view equality (including signed zero), not wider
numeric tolerances. Existing native bnb 0.50.2 tests now run under both `0` and `1`,
including patch forward/backward dispatch, gradients and unsupported-state fallback.
Their launch spies follow the selected engine; unsupported paths forbid both.

Additional direct baseline/candidate tests cover:

- All packed nibble pairs; odd/even lengths and final words with partial bytes.
- Block64, tile4096 and state2-group16384 boundaries, including adjacent tails.
- Changing state2 scales between groups and positive/negative/zero decoded scales.
- Actual Qwen matrix shapes `(1536,1536)`, `(8960,1536)`, `(1536,8960)`, `(256,1536)`.
- Packed transpose and unaligned packed views; destination guards with deliberately
  unaligned but contiguous fp16 output, verifying no overwrite beyond N.
- Flat/nested `out=` reuse, exact live/peak PyTorch allocation equality after warming
  both variants, and prohibition of extra `torch.empty`/`empty_like` calls.

Memory tests are **added, not locally passed** without CUDA. Physical `peak_mib`
from the official paired run remains the final no-increase gate, including any
compiler/driver effects not visible in tensor-allocation assertions.

## Precompile integration completed after takeover

The inherited work already had a separate `nf4_decode_fast_kernel`, but both
public wrappers invoked a dynamic `kernel[...]` alias. The precompiler's AST
scan locates direct named JIT calls, so it found no production launch site for
`nf4_decode_kernel` and raised `no unique production compiler-option sequence`.

`_launch_decode` now contains a direct call to each independently named JIT:
baseline BLOCK2048/4 warps, fast BLOCK4096/8 warps, both with explicit
`enable_fp_fusion=False`. Flat and nested wrappers share this launch helper.
The byte decoder body and its numerical/compiler settings are unchanged.
The existing AST validation was not relaxed or bypassed.

Default preparation retains exactly **62 descriptors / 15 JIT names**.
Only literal `SOUP_EXP_NF4_FAST=1` adds the two nested/flat fast descriptors,
giving **64 descriptors / 16 JIT names**. Baseline descriptors remain unchanged
and available; no fast preparation cost is added when the experiment is off.
Unaligned packed pointers still route to the original kernel.

CPU tests check production launch routing/arguments and both kernels' exact
literal compiler options, signatures and plan selection. CUDA precompile tests
now include fast NF4, alone and combined with EXP-010 CPU launchers: all original
bitwise/cache-hit checks remain, and both independently named NF4 JITs must be
exercised. These CUDA additions are not locally executed.
