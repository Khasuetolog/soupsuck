# EXP-001 — фоновая подготовка Triton и pinned MLP buffers

Статус: реализован opt-in кандидат, **GPU и ускорение UNVERIFIED**.
Включение: `SOUP_EXP_PRECOMPILE=1`; любое другое значение сохраняет прежний
путь. Пустой TRITON_CACHE_DIR перед каждым измеряемым процессом обязателен;
этот эксперимент не меняет и не переносит cache directory.

## Изменение

- `solution/patch.py:install()` запускает `solution.precompile.start()` только
  при буквальном флаге `1`. При обычном apply модуль precompile даже не
  импортируется. Повторный apply не создаёт новые потоки/резервирования.
- Один background thread вызывает `JITFunction.warmup` для 60 описаний
  сигнатур 15 production-кернелов. Несколько описаний могут иметь один cache
  key; 60 — число успешных warmup requests, не число уникальных binaries.
  Компиляция разных вариантов последовательна, без массового compiler pool.
- Второй thread резервирует до 28 пар pinned gate/up `[2048,8960]` fp16
  (1960 MiB host RAM, без GPU staging buffers). Он публикует совместимый
  подкласс существующего `_HostSlot`; готовая пара передаётся ровно одному
  pool slot как views нужной capacity. Размер pool по-прежнему выбирает
  `_pool_for`: например, N=10 даёт capacity=16, а не 2048. Исходные CUDA
  streams/events/leases/DMA policy не меняются. Если резерв ещё не готов,
  capacity>2048 или width другая, используется исходный allocator без ожидания.
- При `SOUP_MLP_OFFLOAD=0` или полном recompute pinned reservation не
  создаётся; partial recompute k уменьшает число резервируемых пар до 28-k.
- `status()` показывает successful warmup requests, ошибки, число созданных
  pinned-пар, finished/alive threads. `wait(timeout)` нужен только тесту и
  ручной диагностике; production install/training его не вызывает.
- Ошибка подготовки печатается в stderr и сохраняется в status. Она не
  заменяет и не отключает training kernel: обычный JIT/allocator остаётся
  доступен. Ошибки реального training path не перехватываются.

Production-кернелы, launch-конфигурации, вычисления модели, порядок батчей и
политики offload/unpad не изменены. Эксперимент EXP-002 коллеги — отдельный
opt-in путь; его новый NF4 matmul не включён в этот перечень.

## Проверка API Triton 3.6

Проверен сохранённый исходник
`/private/tmp/featherduster-triton-3.6.0-jit.py`, соответствующий ранее
извлечённому wheel Triton 3.6.0:

- `KernelInterface.warmup`, строки 358–359: вызывает `run(warmup=True)` и
  превращает dtype в MockTensor. Здесь MockTensor создаются явно, без
  CUDA-активаций и без случайных входов.
- `JITFunction.run`, строки 695–707: **даже warmup получает current device и
  current stream**. Поэтому warmup не является context-free! Фоновый поток
  устанавливает logical CUDA device 0 (целевой single-T4 процесс). Он может
  инициализировать CUDA раньше foreground model load; это часть измеряемого
  запуска. Безопасность concurrent initialization/model load нужно подтвердить
  T4-прогоном, локально её проверить нельзя.
- `run:709–720`: binder формирует specialization/options и общий cache key;
  ищет в `device_caches[device][0]`, компилирует только при отсутствии ключа.
- `run:731–745`: launch вызывается исключительно при `not warmup`.
- `_do_compile:826–854`: без async compile mode результат помещается в тот
  же per-device kernel_cache. Наш код не меняет caches и не создаёт свои
  binaries/serialized specialization файлы.
- `MockTensor:946–970`: data_ptr=0 означает aligned pointer, ptr_range=0 —
  optimistic pointer range. В прогонах реальные tensor allocations aligned;
  иные pointer signatures законно вызовут обычную компиляцию.

Источники API: `triton-lang/triton`, tag `v3.6.0`,
`python/triton/runtime/jit.py`. Код API не копировался и не патчился.
`warmup` также не гарантирует исчезновение launcher/cubin initialization
при первом launch: проверяем именно попадание в JIT cache, а итоговый
first_step_s измеряет все оставшиеся расходы.

## Покрываемые сигнатуры и границы

- RMSNorm: H1536/BLOCK2048/eps1e-6, x/weight fp32, output и upstream
  fp32/fp16. Optional dgamma partial/final также подготовлены, хотя в задаче
  gamma frozen. Runtime group counts имеют aligned/nonaligned варианты.
- Add-RMSNorm: fp32 residual/weight, fp16 delta, оба output dtype; оба grad
  outputs присутствуют, residual grad может требоваться или не требоваться.
- SwiGLU: I8960, tiles4x256, fp16/fp32 projection-output варианты и compressed
  fp16 saved gate/up в backward. Не меняются формулы или autograd boundary.
- CE: logits fp16, state/lse/gain/grad fp32, int64 targets/argmax; FIRST=True
  и False; **реальный tail V151936 % 4096 = 384, BLOCK512** отдельно от
  основных BLOCK4096. dZ BLOCK256 и vector outputs BLOCK256.
- NF4: nested и flat paths, 2048 elements/program; runtime weight counts
  для всех реальных матриц имеют одну alignment specialization.
- LoRA: fp16 adapter, fp16/fp32 base/grad, rounded scale/add и scale backward.
- RoPE: heads12/2, D128, batch1/4, fp16/fp32 cos и q/k, оба grad edges.
  Dense head-major и transposed projection strides имеют одинаковые
  alignment classes; actual stride values остаются runtime.
- N/T=800 и 801 представляют aligned/nonaligned integer specialization;
  это не синтетические тензоры и не constexpr. Pointer dtype и compile
  options совпадают с production. Cache-grid не входит в cache key.

Это не обещание прогрева любого публичного API: новые H/I/eps/dtypes,
all-unused gradient edges, N/T==1-specialization, broadcast upstream и
необычное alignment могут потребовать обычный JIT. Все численные операции
при этом остаются прежними. Гарантия отсутствия реальных cache misses для
известных сигнатур — **ожидаемый результат нового GPU-теста, пока UNVERIFIED**.

превратит фоновую подготовку в обязательную блокировку и изменит гипотезу.

## Ожидаемый эффект и риски

Если 24 s model setup действительно перекрывают warmup и host allocation,
часть ~5 s CPU Triton compile и первой pinned allocation уйдёт из первого
шага. Это гипотеза, не измеренный выигрыш; возможна конкуренция за CPU,
import locks, host RAM и CUDA initialization. Известные цифры 9.88 s first
step и 71.0 s wall относятся к прежнему baseline кандидату, а не к этой
реализации. Решение о выигрыше принимается только по парному прогону.

Резерв имеет верхнюю границу 1960 MiB host RAM, даже если реальный packed
batch использует меньшие views. Поздние непотреблённые пары могут остаться
до конца процесса; они не считаются GPU activation memory и не скрыты от
wall time. Статистика показывает созданные пары, не число использованных.
GPU staging/activation capacity не увеличивается. Compiler и pinned producer
являются daemon threads; foreground никогда не пропускает model/training
work, если они не успели завершить preparation. Оптимизация по умолчанию
выключена до полного подтверждения на T4.
