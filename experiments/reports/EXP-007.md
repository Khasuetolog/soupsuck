# EXP-007 — GPU store для последних k MLP и ранний lookahead

Статус: реализация под opt-in `SOUP_EXP_OFFLOAD_TAIL=k`; **GPU correctness,
wall/CI и peak_mib UNVERIFIED**. Дефолт k=0, дефолты решения не менялись.
Коммит и Kaggle-запуск не выполнялись.

## Основание и принятая политика

Просмотрен `runs_kaggle/20261031T053053884905Z_layerprof_80f8e2e_s043/out/layer_profile.log`:
`mlp.offload.event_wait` — backward 37.3286 ms/step, forward 19.2137 ms/step.
Это профиль контроля, не результат EXP-007. Гипотеза — первые backward MLP
не должны ждать недавно начатый D2H и обратный H2D собственных gate/up.

Получена новая политика координатора (`msg_f35393faba9f`): продвижение только
если peak memory **уменьшился**, а paired same-session wall не медленнее A
(`f4de4e4`); обязательно показать wall_s diff с CI и peak_mib diff.
Memory-only выигрыш — BEST_MEMORY_EXPERIMENT, не дефолт.

Этот кандидат **ожидаемо увеличивает GPU memory**, поэтому не ожидается его
продвижение по этому критерию. Он сохранён только как назначенный opt-in
диагностический эксперимент по времени ожиданий. Без фактических A/B цифр
ни победа, ни соблюдение нового критерия не заявляются.

## Изменение

`solution/mlp.py`:

- `_tail_store()` выбирает последние k MLP по forward depth. Для реального
  Qwen используется общий config.num_hidden_layers и тот же ленивый weak
  depth index, что у partial recompute. `prepare_mlp_offload()` явно размечает
  индексы и общее число MLP, включая модели с раздельными test configs.
- Неизвестная глубина при k>0 и некорректные k отклоняются ValueError; для
  неизвестной глубины можно вызвать prepare_mlp_offload(). Нет догадки,
  какой слой последний. Нулевой/отсутствующий флаг не назначает lazy indices.
- При включённом offload выбранные слои используют существующий GPU store
  путь (те же fp16 saved gate/up). Frozen проекции и backward не меняются.
  Explicit offload=False не включает дополнительные действия. Full/partial
  recompute имеют прежний приоритет и не создают offload ticket.
- Pool резервирует только слои вне recompute prefix и store tail. Для
  пересекающихся префикса/суффикса число offloaded layers равно
  max(0, total-partial-tail). Сохраняется прежняя high-water reservation.
- k>0 включает lookahead двух **offloaded predecessors**, пропуская store и
  recompute слои, которых нет в ticket chain. Три download pairs позволяют
  держать current + two predecessors; k=0 использует прежние два pairs.
- Store-tail context сохраняет только weakref на последний offload ticket.
  В начале его backward два offloaded ticket подгружаются best-effort до
  down_proj backward. Это перекрывает H2D с вычислением последних store MLP.
- Events/record_stream, host leases и запрет evict in-use slot сохранены.
  Изменение lookahead в одном процессе создаёт новый pool, а старый проходит
  прежний retirement/lifetime механизм. Retained graph продолжает владеть
  своими CPU tickets и может быть воспроизведён.

### Forward waits

У текущего offload один общий upload pair. `stream.wait_event(upload_free)`
необходим перед его перезаписью, пока D2H ещё читает те же CUDA buffers.
Он не удалялся: иначе возникнет race либо понадобится ещё один upload pair.
У tail-store слоёв вообще нет upload copy, D2H и соответствующего wait.
Host synchronize и дополнительные main-stream waits не добавлялись.

### Память и трафик: оценки, не результаты

Одна пара gate/up занимает P(N)=4*N*I bytes, I8960. Сохранение k слоёв
добавляет k*P(N); extra download pair — P(C), где C — текущая pool capacity
(обычно next_power_of_two(N)). При оставшихся offloaded слоях ожидаемое
добавление к steady persistent CUDA allocation: k*P(N)+P(C).

| k | N2048,C2048: дополнительная GPU память | Убран D2H, MiB/step | Убран H2D, MiB/step | N800,C1024: дополнительная GPU память |
| --- | ---: | ---: | ---: | ---: |
| 2 | 210 MiB | 140 | 140 | 89.6875 MiB |
| 4 | 350 MiB | 280 | 280 | 144.375 MiB |
| 8 | 630 MiB | 560 | 560 | 253.75 MiB |

Это не peak_mib prediction: peak включает прочие activations, matmul buffers,
allocator reservation и временное сосуществование pools. Если все слои стали
store/recompute, pool вообще не нужен и extra download pair не создаётся.

Process precompile может по-прежнему заранее выделить pinned slots для всех
28 слоёв. Его файл за пределами ownership не менялся: неиспользованные host
slots могут остаться в host RAM, но не являются GPU saved activations.
