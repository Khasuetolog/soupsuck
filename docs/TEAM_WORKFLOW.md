# Командный процесс

Начало работы: [TEAM_SETUP.md](../TEAM_SETUP.md). Общие требования:
[CONTRIBUTING.md](../CONTRIBUTING.md). Приоритет действующих ролей и инструкций
оркестрации сохраняется в [AGENTS.md](../AGENTS.md).

## От задачи к ревью

1. В Issue определите проблему, владельца, сложность, допустимые файлы и приёмку.
2. Fetch origin перед началом. В Orca создайте worktree от свежего `origin/main`,
   проверьте base и имя своей ветки. Названия: `feature/<name>`, `experiment/<name>`,
   `fix/<name>`, `test/<name>`, `docs/<name>`; `main` — только для принятого кода.
3. В Issue укажите ветку и занятые файлы. Независимые worktrees изолируют файлы,
   но не предотвращают конфликт двух PR в одной зоне: назначение согласуйте заранее.
4. Агент получает явный target/change/constraints/ownership/acceptance, а не задачу
   «ускорить всё». Не запускайте второго редактора, пока первый не передал владение.
5. Просмотрите diff, выполните подходящие проверки, сохраните точные команды,
   SHA и логи. Для GPU сначала получите [бронь](KAGGLE_TESTING.md).
6. Commit/Push своей ветки → Draft PR → доказательства → независимое ревью →
   merge ответственным. Если `main` продвинулся, согласуйте обновление ветки через
   merge без переписывания опубликованной истории; после конфликта повторите проверки.

## Зоны владения

| Зона | Типичные файлы | Граница |
|---|---|---|
| CE/indexing | `solution/autograd.py`, `solution/kernels/cross_entropy.py` | Сдвиг labels, маски, scatter/gather, нормировка и метрики |
| Triton kernels | Ядра норм, RoPE, SwiGLU в `solution/kernels/` | Конкретный список файлов; CE/NF4 не занимать автоматически |
| NF4/LoRA/backward | `solution/nf4_patch.py`, NF4-ядра, `solution/lora.py`, `solution/mlp.py` | Dtype, градиенты, offload и stream lifetime |
| Профилирование/проверки | `tools/kaggle/`, собственные `solution/tests/` | Инструментирование только в probe, неизменные jury helpers |
| Документация | `docs/`, командные инструкции, `.github/` | Команды/числа только по исходникам и артефактам |

Это области согласования, не постоянное назначение людей. Общие точки интеграции,
например `solution/patch.py`, имеют одного назначенного владельца. Для пересечения
зон укажите интегратора и порядок применения PR. Корневые `tests/`, `harness/` и
`task/`, включая `task/task.yaml`, не меняются ни в одной зоне.

## Доказательства и честный статус

В PR перечислите команду, окружение, проверенный SHA, результат и ссылку/вложение
лога. Для ошибок нужны минимальный воспроизводимый пример и traceback без секретов.
Счётчик skipped или отсутствие CUDA — «не проверено», а не PASS. Если команда
запущена на другом SHA или с dirty-tree, это явно отмечается и не выдаётся за
проверку текущего diff. GPU-таблица должна содержать baseline, вариант, флаги,
wall/loop/peak/eval и статус checks; данные разных машин не смешиваются.

PR обязателен даже для удачного эксперимента: Summary / Why / Files /
Test evidence / GPU evidence / Risks / Rollback. Ревьюер проверяет фактический
код и логи, а не только вывод агента. Новые изменения после approval требуют
повторной проверки затронутых пунктов.

## Передача и завершение

При передаче оставьте Issue, ветку/SHA, изменённые файлы, известные ошибки,
команды проверок и незавершённые шаги. Не переносите credentials и compiler cache.
В supervised Orca исполнители задают блокирующие вопросы через `ask`, отправляют
ровно один `worker_done` с живыми Task/Dispatch IDs и останавливаются после него.
Для обычного участника достаточно состояния Issue/PR; IDs чужой сессии не копируют.

После merge проверьте видимость изменения в `main`, закройте задачу, освободите
GPU-бронь и затем архивируйте worktree через Orca. Если PR закрыт без merge,
сначала решите судьбу оставшейся работы. Откат принятого изменения — новый revert
PR, не force-push. [Процесс выпуска](RELEASE_PROCESS.md).
