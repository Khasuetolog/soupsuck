# Приёмка и выпуск

Выпуск — решение ответственного за интеграцию после PR, ревью и проверок.
Не означает автоматический upload на Kaggle, push в `main` или публикацию сабмита
любым агентом. Онбординг — [TEAM_SETUP.md](../TEAM_SETUP.md), GPU —
[KAGGLE_TESTING.md](KAGGLE_TESTING.md).

## Перед merge

- [ ] Ветка задачи создана от актуального `main`, PR направлен в `main`.
- [ ] В PR есть Summary, Why, Files, Test evidence, GPU evidence, Risks, Rollback.
- [ ] Ни `harness/`, ни корневые `tests/`, ни `task/`, включая `task/task.yaml`, не изменены.
- [ ] Нет credentials, файлов авторизации, data/model weights, локальных артефактов.
- [ ] Один независимый reviewer одобрил текущий diff; новые коммиты проверены повторно.
- [ ] Для изменения вычислений есть доступные логи проверок и GPU-артефакты того же SHA.
- [ ] Для docs-only вместо CUDA есть обоснованное «не применимо» и проверка ссылок/команд.
- [ ] Конфликты разрешены согласованным владельцем, проверки после разрешения повторены.

Наличие CI само по себе не предполагается. Если автоматизации нет, укажите
выполненные команды и логи вручную. Нельзя отметить checks как пройденные по
обещанию агента или по старому запуску на другом SHA.

## Правила main

Только PR + минимум один approving reviewer; merge выполняет назначенный
интегратор. Прямой push, force-push (в том числе с lease) и удаление `main`
запрещены. Не переписывайте опубликованную историю ради «красивого» PR.

Владелец настраивает branch protection/ruleset с этими ограничениями и, если
возможно, без обхода. Для приватного репозитория возможности зависят от плана:
платный план может потребоваться. Если технической защиты нет, зафиксируйте в
Issue ручной порядок ревью/merge; это не равнозначно серверной защите.
[GitHub: protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Финалист и финальный SHA

1. Выберите кандидата на основании парных измерений и качества, а не одиночного
   удачного времени. Экспериментальный opt-in становится default только отдельным
   проверенным изменением; флаги сдачи должны быть явными.
2. Забронируйте `gpu_benchmark`, зафиксируйте точный SHA, подтвердите чистое дерево
   и запустите `full2`. Проверьте `check_rules`, pytest и качество по артефактам.
3. После merge проверьте, как изменился SHA. Squash/merge commit имеет другой SHA,
   чем ветка: не переименовывайте старые артефакты. Финальная проверка должна быть
   привязана к фактическому коммиту сдачи; при изменении кода прогон повторяется.
4. В выпускном PR/Issue приведите SHA, defaults/env, полный набор checks, wall/peak/eval,
   команды, ссылки на логи и ограничения. Артефакты остаются вне Git, сведения
   должны быть доступны reviewer. Числа в документации берутся только оттуда.
5. Ответственный отдельно подтверждает публичную/внешнюю публикацию. Не создавайте
   релиз, тег, deployment или финальную отправку только потому, что тесты зелёные.
6. После принятия освободите GPU-бронь и закройте Issue; удалите worktree через Orca
   только после проверки сохранности работы и завершения агента.

## Откат

Если изменение ухудшило качество/скорость или сломало checks, остановите его
продвижение. Для ещё не принятого эксперимента вернитесь к контрольному пути без
его opt-in флага и зафиксируйте это в отчёте. Для принятого изменения создайте
`fix/...` worktree от свежего `origin/main` и revert PR с причиной и affected SHA.
Проверки отката и GPU evidence нужны по затронутой области; новый финальный SHA
снова проходит приёмку. Reset/force-push общего `main` не используется.
