# Проверки на Kaggle

Orca управляет файлами и агентами, **GPU он не предоставляет**. Для CUDA нужен
реальный GPU-хост; в этом проекте используется Kaggle T4. У каждого участника
собственный Kaggle-аккаунт и собственная авторизация. Квоты и доступность GPU
проверяйте в своём аккаунте, не предполагая, что они одинаковы у всей команды.

## Подготовка без передачи секретов

1. Создайте свой аккаунт Kaggle и настройте доступ к GPU/API по
   [официальной документации](https://www.kaggle.com/docs/api).
2. Установите Kaggle CLI в личное окружение. Файл `kaggle.json` храните в личном
   каталоге конфигурации CLI **вне репозитория и всех worktrees**; ограничьте
   чтение средствами своей ОС. Не прикладывайте файл к Issue, PR или агенту.
3. Проверьте команды справки. Не публикуйте вывод конфигурации или окружения:
   там могут оказаться credentials. Используйте собственную авторизацию CLI,
   не копируйте чей-либо runtime/config из общей папки.
4. Получите бронь через Issue по шаблону **gpu_benchmark**, согласуйте точный SHA,
   режим и время. Локальный dry-run не расходует GPU и не заменяет эту бронь.

## Бронь и отсутствие конкуренции

В Issue «gpu_benchmark» укажите цель, SHA, режим/варианты/флаги, планируемое окно,
состояние «ожидает / забронировано / выполняется / завершено / отменено» и место
артефактов. Ответственный за координацию подтверждает бронь комментарием; одно
создание Issue ещё не означает разрешение одновременно стартовать несколько jobs.
Перед стартом проверьте другие активные брони. При зависании не стартуйте копию,
сначала выясните статус исходного kernel и зафиксируйте освобождение ресурса.

Одна benchmark-job на Kaggle-сессию, без параллельного обучения/профилирования
на её GPU. Внутри одной `ab` job варианты и база выполняются последовательно —
это один согласованный benchmark, а не несколько конкурентных jobs. Загрузка
нового кода в dataset тоже согласуется: другой прогон не должен получить чужой SHA.
После окончания или отмены обновите Issue и явно освободите бронь.

## Подтверждённые режимы раннера

Список сверен с текущим `python3 tools/kaggle/run.py run --help`, поведение — с
`tools/kaggle/iterate.ipynb`. Перед запуском после обновления ещё раз откройте help.

| `--mode` | Что делает | Для чего результат подходит |
|---|---|---|
| `unit` | Тесты `solution`, затем корневые `tests` с включённым solution | Функциональная проверка; не benchmark |
| `solution` | Тесты solution, официальный `run_task.py --only solution --out runs_try --profile` | Быстрая диагностика, включая отдельный profile run; не сравнение с base |
| `full` | Тесты solution, официальный base + solution, `check_rules`, score | Предварительный полный прогон |
| `full2` | То же, `run_task.py --repeats 2`: base, solution, solution, base | Приёмка финалиста вместе с checks |
| `ab` | Одна база и варианты по раундам с чередованием порядка в одной сессии | Парная оценка эффекта; не сертифицирует checks |
| `bench` | Микробенчмарки `bench_kernels.py` | Поиск параметров ядер; не end-to-end ускорение |
| `layerprof` | Отдельный инструментированный Soup probe, events на шагах 8–24 | Разбор слоёв/forward/backward; не jury timing |
| `probe` | Import-time и cold/warm compile диагностика | Анализ старта/JIT; не benchmark всего обучения |

## GUI-сначала: последовательность запуска

Сначала в Orca просмотрите diff и создайте commit своей рабочей ветки. Через
GitHub Desktop/Orca проверьте SHA и отправьте ветку для PR. Рабочее дерево должно
быть чистым: runner пакует **только committed HEAD**, а не несохранённые изменения.
Точный SHA есть в History/commit view; скопируйте его в бронь и PR.

Сам запуск проекта пока требует команды в терминале этого worktree; это не кнопка
GPU в Orca. После брони и проверки своей Kaggle-авторизации:

```bash
python3 tools/kaggle/run.py run --help
python3 tools/kaggle/run.py run --mode unit --dry-run
python3 tools/kaggle/run.py push-code
python3 tools/kaggle/run.py run --mode unit --tag unit-check
```

`push-code` отправляет committed HEAD в приватный Kaggle dataset; это внешняя
публикация кода в аккаунте запускающего. Перед выполнением проверьте согласованный
SHA и приватность. В этом документе команды приведены для участника; их наличие
не даёт агенту поручения запускать upload/GPU вне назначенной задачи.

Для сравнения двух реализаций в одной сессии, только после проверки, что флаг
реально реализован на выбранном SHA:

```bash
python3 tools/kaggle/run.py run --mode ab \
  --variants 'A=;B=SOUP_EXP_PRECOMPILE=process' --rounds 6 --tag paired-check
```

A — defaults текущего SHA. `--variants` и `--rounds` применимы только к `ab`;
`--env` с `ab` несовместим. Для других режимов есть повторяемый `--env`:
`SOUP_EXP_*` обычно принимает только `1`, `SOUP_EXP_PRECOMPILE` — также `process`.
Флаг не должен молча менять defaults для остальных участников. Не задавайте
`SOUP_APPLY_SOLUTION`: этим управляет официальный путь запуска.

Первый JIT входит в время обучения. Каждый официальный train начинается с пустых
compiler caches; не переносите их из прошлой сессии. Для окончательного кандидата:

```bash
python3 tools/kaggle/run.py run --mode full2 --tag finalist
```

Этот режим уже вызывает `check_rules`; проверьте его лог и все checks, а не только
статус COMPLETE у Kaggle. При ручной проверке в подготовленном GPU-окружении
официальные команды — `python harness/run_task.py --repeats 2`, затем
`python harness/check_rules.py`. Исходники этих helpers менять нельзя.

## Что приложить к PR

`runs_kaggle/` содержит локально скачанные артефакты и **не коммитится**. Дайте
обезличенные имена файлов/относительные пути и доступные reviewer вложения или
ссылки на разрешённые командные артефакты. Один локальный путь у автора не даёт
ревьюеру доступ: приложите нужный лог в PR/Issue, исключив credentials, личные
идентификаторы и содержимое датасета, если его нельзя распространять.

Нужны SHA из source manifest/launch, команда и env-флаги, T4/версии библиотек,
количество повторов и порядок, `result.json`, соответствующие `metrics.json`,
pytest/checks логи, status/exit codes. Покажите wall, loop/median step, peak memory,
eval и долю own kernels с источниками чисел. Для `ab` добавьте успешные пары,
медиану разницы и интервал; данные разных сессий не объединяйте в одно сравнение.

`probe`/`bench`/`layerprof` могут менять стоимость измерения инструментированием;
их ускорение нельзя выдавать за `full2`. Skipped, interrupted, failed и отсутствие
GPU перечисляются отдельно. После изменения кода измерения старого SHA не
становятся доказательством нового: финалист повторяет `full2 + check_rules`.
