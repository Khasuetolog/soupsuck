# Команда хакатона

Актуальная схема по просьбе пользователя: **Claude Code — главный оркестратор;
Codex — два исполнителя с разными аккаунтами**. Пользователь выбрал Claude Code
Opus 5.5 (`claude-opus-5-5`) и разрешил использовать оба найденных аккаунта Codex.
Эти проектные роли заменяют
прежнюю схему Codex → Gemini. Не подменять провайдера или модель без ответа пользователя.

## Общение

- Общаться с пользователем на русском.
- Уточнять требования кейса, критерии оценки, спорные продуктовые решения и
  недостающие доступы. Не угадывать предпочтения пользователя.
- Задавать короткие, конкретные вопросы с вариантами, когда это полезно.
- Продолжать независимую работу, пока ожидается ответ. Не выполнять зависимую
  часть до ответа, если он нужен для правильного результата.
- Обычные обратимые технические действия в рамках задачи выполнять самостоятельно.

## Роли и ответственность

- Claude разбирает кейс, согласует открытые вопросы, планирует, пишет задания,
  распределяет владение файлами, проверяет изменения и результаты тестов,
  интегрирует принятые изменения и сообщает пользователю итог.
- Codex-1 и Codex-2 выполняют только назначенные задания. Перед первым запуском
  подтвердить разные аккаунты. Нельзя считать две сессии одним доказательством
  двух аккаунтов.
- Конкретное разделение работ определить после получения кейса. Не закреплять
  заранее стек или frontend/backend, пока требования неизвестны.
- Codex-3 — возможный резерв. Добавляется после подключения пользователем.
  Не запускать заранее и не заменять им живого исполнителя без проверки состояния.

## Orca

Использовать установленные навыки `orca-cli` и `orchestration`, загрузив
версионные инструкции через выбранный для сессии исполняемый файл Orca.
Не заменять Orca workers внутренними субагентами.

Для контролируемой реализации связать Run и запускать исполнителей через
`orchestration worker-start --spec ... --worktree ... --agent codex --json`.
Для исполнителей Codex модель наследовать из настроек, пока пользователь явно
не выбрал другую. Для координатора Claude использовать `claude-opus-5-5`.
Проверять effective launch и фактическую привязку аккаунта; не выдумывать
параметр CLI для выбора аккаунта, если его нет в текущем `--help`.

Каждое задание должно содержать цель, изменение, ограничения, сложность,
владение файлами и наблюдаемые критерии приёмки. Шаблон:
`orchestration/task-template.md`.

Не допускать одновременных правок одних файлов. Независимые области можно
распределять внутри одного checkout; если нужна изоляция, создавать worktree
через Orca и явно выбирать правильную базу. Не выполнять checkout/reset/merge
в общем checkout, пока другой исполнитель редактирует его.

Работники соблюдают живой Task/Dispatch preamble, задают блокирующие вопросы
координатору через `ask` и отправляют ровно один `worker_done` с реальным outcome.
Координатор обрабатывает вопросы, проверяет diff и тесты, а после settlement
переиспользует, явно сохраняет или освобождает worker согласно навыку.
Не сообщать о завершении без проверяемого результата.

## Лимиты и передача работы

При лимите сохранить доступный прогресс: файлы, текущую задачу, результаты
проверок и точный текст ошибки без секретов. Сообщить пользователю, какой
исполнитель остановился и что осталось. Не обещать автоматического переключения
аккаунтов без проверенной поддержки. Не запускать второго редактора той же
области, пока владение предыдущего не урегулировано по правилам Orca.

Новый аккаунт получает контекст, границы правок и оставшиеся критерии приёмки.
Уже выполненное не начинать заново. Пароли, токены и файлы авторизации не
копировать в репозиторий, задания, отчёты или чат.


## Командная работа

Эти правила дополняют назначенные выше роли и live Task/Dispatch, не заменяя их.
Онбординг: [TEAM_SETUP.md](TEAM_SETUP.md); общий процесс:
[CONTRIBUTING.md](CONTRIBUTING.md) и [TEAM_WORKFLOW.md](docs/TEAM_WORKFLOW.md).

- Каждая задача имеет Issue, владельца файлов, критерии приёмки и отдельный
  worktree от свежего `origin/main`; перед началом выполнить fetch. Рабочие ветки:
  `feature/<name>`, `experiment/<name>`, `fix/<name>`, `test/<name>`, `docs/<name>`.
  Не редактировать одновременно чужие файлы и не переключать общий checkout.
- Не изменять `harness/`, корневые `tests/` и `task/`, включая `task/task.yaml`.
  Разрешённые собственные тесты/инструменты определяются назначенным заданием.
- Не пушить напрямую в `main`, не удалять `main`, не выполнять force-push,
  включая force-with-lease. Принятие изменений — через PR и независимое ревью.
- Не копировать credentials, токены, файлы авторизации, `kaggle.json` или `.env`
  в репозиторий, задания, сообщения, PR и логи; использовать свои аккаунты и подписки.
  Личные идентификаторы и локальные пути не нужны в публикуемых доказательствах.
- Не объявлять тесты/GPU/checks пройденными без команды, точного SHA и доступных
  логов. Failed/skipped/not run перечислять отдельно; старый SHA не проверяет новый diff.
- Каждый PR обязателен с разделами **Summary / Why / Files / Test evidence /
  GPU evidence / Risks / Rollback**; для docs-only GPU evidence допускает
  обоснованное «не применимо». Нужен минимум один независимый reviewer.
  После новых коммитов обновить evidence и запросить повторное ревью.
- Для GPU сначала получить эксклюзивную бронь Issue `gpu_benchmark` по
  [KAGGLE_TESTING.md](docs/KAGGLE_TESTING.md). Не запускать конкурентные jobs;
  финалист проходит `full2` + `check_rules`. Артефакты `runs_kaggle/` не коммитить.
- Наличие шаблонов и команд не авторизует агента на commit/push, публикацию PR,
  upload в Kaggle или финальную отправку вне явно назначенной задачи.
  При недоступной технической защите приватного репозитория соблюдать явную
  политику PR + ревью; не считать её включённой автоматически.
