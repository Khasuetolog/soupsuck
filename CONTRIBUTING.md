# Как участвовать

Новичку: начните с [TEAM_SETUP.md](TEAM_SETUP.md). Повседневный процесс описан в
[TEAM_WORKFLOW.md](docs/TEAM_WORKFLOW.md), GPU-проверки — в
[KAGGLE_TESTING.md](docs/KAGGLE_TESTING.md), выпуск — в
[RELEASE_PROCESS.md](docs/RELEASE_PROCESS.md).

## Один Issue → одна ветка → один worktree → один PR

1. Создайте Issue с целью, границами файлов, владельцем, проверками и ожидаемым
   результатом. Для ускорений используйте шаблон `optimization_experiment`.
2. Выполните Fetch origin, создайте в Orca отдельный worktree от свежего
   `origin/main`. Не продолжайте чужую ветку без явной передачи задачи.
3. Выберите ветку по назначению:

   | Ветка | Назначение |
   |---|---|
   | `main` | Принятые изменения; только через PR |
   | `feature/<name>` | Новая возможность |
   | `experiment/<name>` | Проверяемая гипотеза ускорения |
   | `fix/<name>` | Исправление ошибки |
   | `test/<name>` | Проверки и диагностические инструменты |
   | `docs/<name>` | Документация |

4. Согласуйте владение файлами до запуска агента. У каждого участника собственные
   учётные записи и подписки; существующие роли оркестрации сохраняются в
   [AGENTS.md](AGENTS.md) и [CLAUDE.md](CLAUDE.md).
5. Измените только согласованные файлы. Просмотрите diff, выполните нужные проверки,
   сохраните логи с SHA проверенного кода. Отсутствие GPU отметьте прямо.
6. Через GUI сделайте commit, Push своей ветки и PR в `main`. Заполните
   [шаблон PR](.github/pull_request_template.md), назначьте независимого ревьюера.
7. После замечаний добавляйте новые коммиты. После merge удаляйте worktree только
   когда нет незакоммиченной работы и подтверждено завершение агента.

## Неподвижные границы

- Не менять `harness/`, корневой `tests/`, `task/`, включая `task/task.yaml`.
  Их разрешено читать и запускать. Собственные тесты в `solution/tests/` меняются
  только в назначенной зоне задачи.
- Не пушить прямо в `main`, не применять force-push, включая force-with-lease,
  не удалять `main`. Исправления истории не заменяют ревью.
- Не коммитить credentials, `kaggle.json`, файлы авторизации, `.env`, локальные
  выгрузки, `team-share/`, crash bundles и `runs_kaggle/`. Не помещать секреты
  в Issue, PR, скриншоты или контекст агента. `.gitignore` не удаляет уже
  отслеживаемый файл и не стирает секрет из истории.
- Не считать зелёный текст агента доказательством тестов. Нужны команда, SHA,
  итог и доступный лог; skipped и not run не равны passed.
- Эксперименты не меняют defaults без отдельного решения и проверок. Ускорение
  не оправдывает изменение математики, датасета, trainer args или пропуск работы.
- Ошибочный benchmark сохраняется как failed, а не исчезает из отчёта.

## Что должно быть в PR

Summary, Why, Files, Test evidence, GPU evidence, Risks, Rollback: что изменено,
зачем, какие файлы затронуты, чем проверено, где артефакты GPU, что может сломаться
и как откатить. Для docs-only GPU можно указать «не применимо» с причиной.
Для изменения вычислений без CUDA-проверки PR остаётся Draft до её получения.
Минимум один независимый reviewer должен одобрить текущий diff; после изменений
по замечаниям нужна повторная проверка. Merge выполняет ответственный за интеграцию.

## Если что-то пошло не так

Остановите зависимую работу, сохраните diff и обезличенную ошибку в Issue.
Не выполняйте reset/clean или переключение ветки в checkout, где работает другой
участник. При конфликте владельцев файлов сначала согласуйте передачу. Если секрет
уже опубликован, сразу отзовите его у провайдера и сообщите владельцу репозитория,
не повторяя сам секрет в сообщении.
